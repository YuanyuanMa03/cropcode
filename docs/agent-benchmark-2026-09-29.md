# CropCode Agent 基准测试（2026-09-29）

这是一次本机探索性测评，不是公开排行榜。测试对象是已安装的 CropCode 1.1.0 与本机打包的 CropCode 2.0.0，各自通过真实 CLI 和 macOS 桌面界面运行。四组均使用本机配置的火山方舟 Coding Plan `glm-5.3`；每格只运行一次，没有控制模型采样、推理强度或并发负载，因此不能把差异单独归因于内核。

题库、原始数据、原始错误实现及隐藏评分器位于 [基准测试目录](../benchmarks/crop-agent-v1/README.md)，逐项结果另存为 [JSON](../benchmarks/crop-agent-v1/results-2026-09-29.json)。首轮运行前，八个输入文件的 SHA-256 已写入 `manifest.json`，运行后逐项复核均未变化。每题 100 分：九项隐藏行为检查各 10 分，原始 CSV 字节不变 10 分。评分器实际导入各独立工作区内 Agent 修改的 Python 文件，在新建的临时 CSV 上运行检查；不使用 Agent 的自述或其自建测试判分。未修复的原始实现两题均为 20/100。

| 界面与版本    |                    积温修复 A |     产量率定/独立验证 B | 完成情况                                         |
| ------------- | ----------------------------: | ----------------------: | ------------------------------------------------ |
| CLI 1.1.0     |            100/100，229.36 秒 |      100/100，419.63 秒 | 两题正常返回                                     |
| CLI 2.0.0     |            100/100，526.34 秒 |     100/100，600 秒截止 | B 的代码通过隐藏检查，但进程超时，未返回最终答复 |
| Desktop 1.1.0 |                       100/100 |                 100/100 | 两题均在界面给出最终答复，各约 10 分钟           |
| Desktop 2.0.0 | 100/100，界面显示 30 分 28 秒 | **20/100，10 分钟截止** | A 最终返回；B 截止时仍为原始代码，未返回最终答复 |

两题均包含科研计算约束：A 要处理 10–30 ℃ 截断、缺测、重复日期和排序；B 必须只在率定集拟合偏差，再在独立验证集计算 MAE、RMSE、MBE，并检查非法分区、缺测和重复样方。旧版 CLI 与 Desktop 都得到 200/200 的最终代码分数。新版 CLI 的最终文件也是 200/200，但 B 超过 600 秒运行上限。新版 Desktop 截止/停止时为 120/200；其中 A 用时远超 10 分钟，B 在 10 分钟时仍为 20 分。因此代码正确率与按时自主完成率必须分开看。

**可比性限制。** B 的四次运行都收到同一短指令，要求读取各自工作区的 `PROMPT.md` 并完成修复。A 的新版 Desktop 输入遭到富文本编辑器/自动化输入损坏，实际发送内容只保留了部分代码标记；Agent 仍自行读取了 `PROMPT.md` 并修复，但这一格不能视为严格同提示词对照。新版 CLI 的 A 首次使用默认 build 模式时无输出并在 600 秒超时；表中记录的是干净工作区以显式 `--mode yolo` 重跑的结果。旧版 CLI 使用其 `--exec` 模式。新版 Desktop 的 A 多次等待一次性文件/命令权限，所列 30 分 28 秒包含人工处理等待；B 在截止后才进入写入权限，随后写入工具报告失败。桌面耗时是界面读数或近似观察值，不适合与 CLI 秒级数字排序。

结论是：现有样本支持“四个入口都能完成至少一项真实代码修复”，但不支持“2.0.0 Agent 已优于旧版”。这次更清楚地暴露了 2.0.0 的长推理/压缩、权限等待与截止时间内完成率问题。需要先针对这些路径修复和复测，再扩大到多种作物模型任务、多个种子及独立审题集。
