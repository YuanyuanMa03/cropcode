# CropCode Agent benchmark (2026-09-29)

This is a local exploratory evaluation, not a public leaderboard. The installed CropCode 1.1.0 and locally packaged CropCode 2.0.0 were exercised through their real CLI and macOS desktop interfaces. All four used the locally configured Volcengine Coding Plan `glm-5.3`. Each cell has one run. Sampling, reasoning effort, and concurrent load were not controlled, so differences cannot be attributed to the kernel alone.

The tasks, raw data, buggy starting implementations, and hidden grader are in the [benchmark directory](../benchmarks/crop-agent-v1/README.md), with per-check [JSON results](../benchmarks/crop-agent-v1/results-2026-09-29.json). SHA-256 values for the eight original input files were frozen in `manifest.json` before the first run and verified unchanged afterwards. Each task has 100 points: nine hidden behavior checks worth 10 points each, plus 10 for preserving the original CSV bytes. The grader imports each agent-modified Python file from its isolated workspace and exercises it on new temporary CSV files. Agent summaries and self-authored tests do not determine the score. Both unmodified starting implementations score 20/100.

| Interface and version |            Degree-day repair A | Yield calibration/holdout B | Completion                                                                              |
| --------------------- | -----------------------------: | --------------------------: | --------------------------------------------------------------------------------------- |
| CLI 1.1.0             |              100/100, 229.36 s |           100/100, 419.63 s | Both returned normally                                                                  |
| CLI 2.0.0             |              100/100, 526.34 s | 100/100 at the 600 s cutoff | B passed hidden checks on disk but timed out without a final response                   |
| Desktop 1.1.0         |                        100/100 |                     100/100 | Both returned final answers, roughly 10 minutes each                                    |
| Desktop 2.0.0         | 100/100, UI showed 30 min 28 s |    **20/100 at 10 minutes** | A eventually returned; B still had the original code at cutoff and gave no final answer |

Both tasks impose scientific-computing constraints. A covers 10–30 °C capping, missing observations, duplicate dates, and ordering. B fits bias only on calibration observations, then computes MAE, RMSE, and MBE on independent validation rows, with checks for invalid partitions, missing values, and duplicate plots. The older CLI and Desktop both produced 200/200 final code. The newer CLI also had 200/200 on disk, but B exceeded the 600-second limit. The newer Desktop had 120/200 at cutoff/stop; A took far longer than 10 minutes, while B remained at 20 points at 10 minutes. Code correctness and on-time autonomous completion are separate outcomes.

**Comparability limits.** All four B runs received the same short instruction to read their workspace's `PROMPT.md` and repair the code. The new Desktop's A input was mangled by the rich-text editor/computer input path: the submitted message retained only some code tokens. The agent read `PROMPT.md` and repaired the file, but that cell is not a strictly matched-prompt comparison. The new CLI's first A attempt in default build mode produced no output and timed out after 600 seconds; the table records a clean rerun with explicit `--mode yolo`. The old CLI used its `--exec` mode. The new Desktop's A waited repeatedly for one-time file and command permissions; its 30 min 28 s includes human approval waits. B reached a write permission only after the cutoff, and the write tool then reported failure. Desktop durations are UI readings or approximate observations and should not be ranked against the CLI's second-level timings.

These samples show that all four entry points can complete at least one real code repair. They do not show that the 2.0.0 Agent outperforms the old version. The clearest 2.0.0 issues exposed here are long reasoning/context compaction, permission waits, and on-time completion. Fix and rerun those paths before expanding to multiple crop-model tasks, seeds, and an independently prepared test set.
